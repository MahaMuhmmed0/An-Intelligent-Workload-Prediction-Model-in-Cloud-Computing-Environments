Section 01

The two datasets

Both traces record what cloud workloads asked for and what they actually used. They differ in structure, in what a "usage" number means, and in what modelling they can support.

Google 2019 Cluster

Borg trace v3 · public extract

file
borg_traces_data.csv — ≈406 K instance-usage rows, 34 columns
request
resource_request → {cpus, memory}, dict-encoded
usage
average_usage, maximum_usage → {cpus, memory}; cpu_usage_distribution (11 percentiles)
units
CPU in NCU, memory in normalised bytes — both divided by the largest machine's capacity, so both lie in [0, 1] on one scale
time
31-day span; rows are per-instance 5-minute windows, sampled sparsely (median 4 distinct hours per machine)

Alibaba 2017

cluster-trace-v2017

files
container_event, container_usage (1.48 M rows), server_usage (188 K rows)
request
plan_cpu (core count), plan_mem, plan_disk (normalised)
usage
cpu_util, mem_util — percentage of the instance's own request (0–100)
units
utilisation ratio; the request magnitude has largely divided out
time
12 continuous hours; server_usage is dense machine-level telemetry at 5-minute resolution

One consequence to state up frontBecause Google usage is an absolute normalised quantity and Alibaba usage is a ratio to the request, only R² is comparable across the two datasets — MAE and RMSE are in different units. This difference is also the main reason Google usage turns out far more predictable from the request than Alibaba usage.

Section 02

Original Google 2019 Cluster method, as reconstructed

This section is a historical audit record — it is not the methodology used for the final results. The final, corrected methodology is Section 04. There was no written spec; the description below is read directly from the pre-rebuild notebooks that predated this repository. All models shared one preparation path.

Tabular models — Linear, Ridge, Lasso, Elastic Net, Stepwise, Random Forest

  1. Parse. cpu_usage_distribution string → array via eval(x.replace(" ", ", ")); resource_request → cpu_request, memory_request via ast.literal_eval.
  2. Engineer. mean_cpu_usage (the target), plus std_cpu_usage, max_cpu_usage, min_cpu_usage and cpu_memory_ratio = mean_cpu_usage / (assigned_memory + 1e-5).
  3. Assemble. keep every numeric column as a feature; SimpleImputer(strategy="mean") over the whole frame.
  4. Expand. Stepwise / Lasso / Elastic Net add PolynomialFeatures(degree=2).
  5. Split. train_test_split(test_size=0.2, random_state=42), shuffled.
  6. Scale. MinMaxScaler (Linear/Ridge/RF) or StandardScaler (the rest), fit on train.
  7. Select / tune. Stepwise = LassoCV(cv=5) → keep non-zero coefficients → refit OLS. Lasso / Elastic Net = GridSearchCV(cv=5, scoring="neg_mean_absolute_error").
  8. Evaluate. MAE, MAPE, R² on train and test.

Memory notebooks use memory_request as the target rather than a usage quantity.

Sequence models — LSTM, BiLSTM, RNN

  1. Series. take the mean_cpu_usage values in file order.
  2. Clean. IQR outlier removal on the series; log1p (LSTM); MinMaxScaler over the whole series.
  3. Window. create_sequences with length 50–100; chronological 80/20 split X[:k], X[k:].
  4. Model. stacked 128-64-32, Dropout 0.3, Dense(1); Adam(1e-4), Huber loss; EarlyStopping + ReduceLROnPlateau; validation_split=0.1.
Section 03

Methodological problems found

The Alibaba re-implementation is a different, weaker adaptation of the same idea — its problems are severe. The Google notebooks are closer to sound; their problems are moderate.

Alibaba re-implementation severe

A1
The target column sits inside the feature list
features contains cpu_usage_server, which is also the target. The model learns the identity.
Effect: R² = 1.0000, MAE = 0 — this is the "100 %" result, and it is the bug.
A2
Invented column names
Columns labelled disk_io, network_io, unknown1/2. The real schema is disk_util%, load1, load5, load15; Alibaba 2017 has no network column at all.
Every feature name in the write-up would have been wrong.
A3
A join between two unrelated tables
merge(server_usage, container_usage, on="time") pairs a machine's utilisation with an arbitrary unrelated container measured in the same window, many-to-many.
The resulting dataset has no physical meaning.
A4
Stepwise selection reads the test set
Each feature is added to minimise mean_absolute_percentage_error(y_test, …).
Selection must see training data only.
A5
Shuffled split of overlapping windows
60-step windows are built, then train_test_split(shuffle=True) scatters near-identical adjacent windows across train and test.
Effect: R² ≈ 0.9995 for the regularised regressors, purely from leakage.
A6
Scaler fit on all data; test set used as validation
fit_transform before the split, and validation_data=(X_test, y_test) with restore_best_weights — the epoch is chosen on the test set.
Both leak test information into training.
A7
Arbitrary down-sampling
iloc[::500] — a "60-step window" then spans days of wall-clock time.
Destroys the temporal spacing the sequence models depend on.

Original Google 2019 Cluster notebooks moderate

G1
Circular target–feature relationship
mean_cpu_usage is predicted from std / min / max of the same 11-value percentile vector. That is describing the sample, not predicting it.
Inflates R² to 0.95–0.98. Rebuild uses average_usage as the target and drops distribution-derived features.
G2
Identifiers kept as numeric features
collection_id, machine_id, instance_index, time, start_time, end_time, cluster all enter the model.
Noise, and a route for time leakage. Dropped in the rebuild.
G3
Memory models predict the request, not the usage
Target is memory_request; cpu_memory_ratio is derived from the target. The spec confirms usage is average_usage.memory / assigned_memory.
Rebuild predicts memory usage and forms the ratio from requests only.
G4
Imputer and polynomial expansion fit before the split
Column means and feature statistics see the test rows.
Minor leakage; moved inside an sklearn Pipeline.
G5
MAPE is meaningless here
Usage is frequently ~0, so reported MAPE runs to 10¹¹–10¹³ %.
Report MAE, RMSE, R² and a guarded sMAPE instead.
G6
Sequence models fed a non-temporal bag of instances
mean_cpu_usage in file order is a set of unrelated jobs, not a time series.
Correctly rebuilt (Section 09) — and the extract still cannot support forecasting.
Section 04

The corrected unified pipeline

This is the final, authoritative methodology. It is implemented in src/ (the source of truth); the notebooks/ contain the same logic verbatim. One codebase, two thin dataset adapters that project each trace onto the same contract: features are the resource request plus permitted static metadata; targets are observed usage only; nothing derived from a target is ever a feature.

  1. Adapter. Google: parse the three dict columns. Alibaba: aggregate container_usage per instance, join container_event requests. Both emit cpu_request, mem_request, cpu_mem_ratio + metadata + cpu_usage / mem_usage (mean and peak).
  2. Split. the regression task is cross-sectional — predict an unobserved property of a job from its request — so a random 80/20 split is used (matching the original); a chronological split is kept for sensitivity checks.
  3. Robust preprocessing. log1p on non-negative skewed features and winsorising to the training 1st/99th percentiles — bounds from train only — so degree-2 polynomial terms cannot extrapolate wildly.
  4. Pipeline. SimpleImputer → PolynomialFeatures → Scaler → model, so every fitted transform sees training folds only. GridSearchCV(cv=5) on the training partition.
  5. Stepwise. embedded LassoCV selection then OLS refit, entirely within training data.
  6. Sequence models. genuine per-machine series; per-series chronological split; scaler fit on training windows only; no window straddles the boundary; validation = tail of train, never the test set.
  7. Metrics. MAE, RMSE, R², guarded sMAPE — reported for train and test so any train/test gap is visible.

Section 06

What cannot be mapped

  • Network I/O — does not exist in Alibaba 2017. The original Alibaba notebooks invented it.
  • Priority / scheduling class for containers — Alibaba exposes these for batch tasks only, not the online containers used here.
  • Pre-computed usage distributions — Google's cpu_usage_distribution / tail_cpu_usage_distribution percentile vectors have no Alibaba equivalent; comparable statistics would have to be computed from each instance's own container_usage rows.
  • CPI / MPKI at request time — Alibaba records these only as usage outputs, not as inputs available before scheduling.
  • A machine-level utilisation time series on Google — see Section 09.

Section 09

The sequence-model finding on Google 2019 Cluster

The Google sequence experiment was rebuilt correctly — a cell-level hourly aggregate of average_usage over the 31-day span, missing buckets interpolated, chronological split, scaler on train only. It still fails, and the reason is the data, not the model.

Autocorrelation at lag (hours)12361224
Google 2019 Cluster — cell series (noise band ±0.072)0.01−0.030.010.03−0.01−0.01
Alibaba 2017 — cell series (noise band ±0.163)0.870.820.790.700.540.55

The public borg_traces_data.csv is a random cross-sectional sample of instance-usage records — 1 to 9 907 rows per hour, no machine-level continuity. Its autocorrelation is inside the noise band at every lag, including lag 24 where a real datacenter signal shows a strong diurnal peak. LSTM, BiLSTM and RNN all score R² ≈ 0 on it.

DecisionThe two traces support different modelling paradigms. Google 2019 Cluster → cross-sectional provisioning regression only. Alibaba 2017 → regression and temporal forecasting. The paper presents the LSTM/BiLSTM/RNN results on Alibaba and reports the Google extract's lack of temporal structure, with the autocorrelation table as evidence.
